## Contract and source notes

### Authority

Register names and descriptions come from the supplied Crop and Down scaler screenshots. The Resampler slide supplies the divisibility-by-8 and output/input ratio [1/8, 7/8] limits. The boundary document proposes consistency and edge policies; it does not establish exact C55 hardware behavior. Validation rules and software controls here are the adopted wrapper contract.

### Input and future YUV

This version accepts only nonempty uint8 RGB arrays with three full-resolution channels and RGB image files. Eventual pipeline input will be YUV. YUV is not interchangeable with RGB; layout, chroma subsampling, range and conversion must be specified during future integration. No YUV conversion is implemented.

### Fixed-point bilinear

The wrapper calls unchanged ocr_bench.resample.fixed_point_bilinear independently per channel. It uses floating-point coordinate/coefficient setup, 11 fractional coefficient bits, and integer pixel accumulation with existing OpenCV-compatible rounding and special cases. It does not call OpenCV or the floating-point bilinear function. This is not an integer-only or hardware-bit-exact model.

### Increments and dimensions

The wrapper assumes unsigned Q4.20 and checks truncation using integer division. Increments validate dimensions but do not drive sampling. Output dimensions are explicit, so the slide's output-size rounding step is not exposed as a scale-input API. No undocumented hardware address, storage width, dimension maximum, or bank contents are assigned.

### Sampling and boundaries

Original samples x=u*W/M; shift samples x=(u+1/2)*W/M-1/2. Nearest uses exact rational coordinates and round-half-up indices. Average uses the four floor/floor+1 neighbors and (sum+2)//4, not area averaging. Clamp every selected neighbor to the effective crop edge. RGB channels are sampled independently without color conversion.

### Frame validation

All 16 fields are required integers (booleans excluded). Unknown and duplicate JSON keys are rejected. Inactive crop geometry is ignored after type validation. Array shape is the available frame extent; cropped dimensions must match scaler registers. Short or malformed decoded input fails; border extension never supplies missing frame data. Stream framing is outside this array/file interface.

### Scale limits

Both effective scaler input dimensions must be divisible by 8, even when crop is inactive. Each output/input ratio must lie in [1/8, 7/8]. Identity and enlargement are rejected. An 8x8 input may produce 1x1 output; odd output dimensions are allowed. These slide limits are stricter than general bilinear mathematics.

### Coefficient selectors

Both selectors accept only zero as an inactive placeholder. No coefficient LUT is loaded or executed. This does not claim hardware bank zero is bilinear. Coefficient signedness, numerical normalization, and the hardware phase-selection rules were not supplied.

### LUT index discrepancy

The screenshot labels its last set-15/phase-31 rows as 511 and 512. The stated 16 sets x 32 phases x 2 words instead implies 1024 words, indexed 0-1023. Under sequential packing, word0=64*set+2*phase and word1=word0+1; the final pair would be 1022/1023. This arithmetic is an inference, not a correction to verified hardware documentation.

### Horizontal ratio typo

The hfilt_tinc screenshot describes horizontal input/output heights. The wrapper uses widths, consistent with the horizontal axis and width_in/owidth.

### Hardware port

Python integers prevent overflow in validation and nearest/average coordinate arithmetic. A C port must bound dimensions and choose widths for shifts, coordinate products and addresses; four uint8 samples sum to at most 1020. Hardware equivalence still requires verified phases, coefficients, intermediate precision, rounding, border behavior, formats and limits.
