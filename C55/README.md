# C55 crop and row-streaming resampler

C55 implements a register-driven software reference with three stages: frame
setup, coordinate/phase generation, and interpolation. It supports nearest,
32-phase LUT bilinear, and translated 2×2 average. All processing lives in `C55/`;
the independent `ocr_bench.resample` benchmark kernels remain unchanged.
This model does **not** establish bit-exact C55 hardware behavior.

**Input is 8-bit RGB only.** Future YUV support requires explicit layout,
subsampling, range, and conversion decisions. No color conversion is performed.

## Run from the repository root

Use the existing project environment, or install with `python -m pip install -e '.[dev]'`.
Generate the coefficient file after a fresh checkout, then run the resampler:

```sh
.venv/bin/python -m C55.generate_coefficients --output C55/bilinear_coefficients.json
mkdir -p C55/outputs
.venv/bin/python -m C55.resampler --input input.png --registers C55/registers.example.json --output C55/outputs/output.png
```

The example crops **168×168 at (0, 0)** and produces **64×64**, with original
mapping and both increments set to **2,752,512 = 2.625 × 2^20**. The source must
be at least 168×168. Larger source frames are still fully validated.

Input image mode must be `RGB`; other modes are rejected. Output is lossless
PNG regardless of its filename suffix. The image CLI decodes and collects whole
frames; use the row API for bounded processing memory. Errors exit nonzero
before saving output.

| Software-only field | Values | Example |
| --- | --- | --- |
| `Resampler: method` | `0` nearest, `1` LUT bilinear, `2` translated 2×2 average | `1` |
| `Resampler: interpolation` | `0` original, `1` shift (half-pixel) | `0` |

All 16 register fields are required JSON integers. Booleans, floats, strings,
unknown keys, and duplicate keys are rejected. See [registers.md](docs/registers.md)
and [registers.xlsx](docs/registers.xlsx) for the complete register reference.

## Python interfaces and streaming lifetime

```python
from C55.resampler import crop_and_resize, load_registers, resize_rows
from C55.generate_coefficients import load_coefficients

registers = load_registers("C55/registers.example.json")
coefficients = load_coefficients()  # Locally PC-generated bank.

# Array adapter: image is a nonempty RGB uint8 array shaped (height, width, 3).
output = crop_and_resize(image, registers, coefficients=coefficients)

# Streaming interface: source_rows yields full-frame arrays shaped (width, 3).
for output_row in resize_rows(
    source_rows, registers, frame_shape=(frame_height, frame_width, 3),
    coefficients=coefficients,
):
    consume(output_row)
```

`resize_rows(rows, registers, *, frame_shape, coefficients=None)` validates and
copies configuration and coefficients when called, before consuming any input.
`frame_shape` describes the full frame before cropping. The iterator consumes
rows in raster order, crops incrementally, and yields independent RGB `uint8`
rows. Producers may reuse their row storage after each yield. Later mutations
to the caller's configuration or coefficient dictionary do not affect this frame.
`None` coefficients loads the locally generated bank; supplied coefficients are a dictionary
returned by `load_coefficients(path)`.

Horizontal filtering produces widened rows; vertical filtering retains only
rows needed for the next output. The buffer holds at most seven filtered rows
(and at most two with the currently supported bilinear/average kernels), plus
one input row and output-sized working arrays. No full-frame intermediate or
full-axis coordinate table is allocated. The generator uses ordinary iterator
backpressure; clock-cycle valid/ready handshakes are not modeled.

**Exhaust the iterator to validate the frame.** Every input row must have the
specified width, three channels, and `uint8` dtype, including skipped rows before
and after the crop. Missing and extra rows raise `ValueError`. Outputs remain
provisional until successful exhaustion: errors in trailing input may follow the
last output row. Stopping iteration early leaves the remaining input unchecked.

`crop_and_resize(image, registers, *, coefficients=None)` collects this same
streaming implementation into an independent output array, leaving inputs
unchanged. The array adapter and CLI complete validation before returning/saving.

## Stage 1: frame setup

Software (SE) supplies dimensions and increments; the model validates rather
than overwrites them. Settings remain fixed for a frame.

1. Crop is active only when `Pipeline: Bypass crop=0` and `Crop: Enable crop=1`.
   Bypass wins. Inactive crop geometry is ignored after integer-type checks.
   Active origins must be nonnegative, sizes positive, and the crop wholly
   inside the declared frame.
2. `width_in` and `height_in` must equal effective crop dimensions, or full-frame
   dimensions with inactive crop. Both must be divisible by eight.
3. Outputs are explicit positive dimensions, with
   `input <= 8 * output <= 7 * input` on each axis. Identity/enlargement are
   rejected; odd outputs and 8×8 → 1×1 are valid. No automatic output-size rounding.
4. Require `hfilt_tinc == (width_in << 20) // owidth` and
   `vfilt_tinc == (height_in << 20) // oheight`, within unsigned Q4.20 range
   `[2^20, 2^24-1]`. Integer arithmetic prevents validation overflow.
5. Both coefficient selectors must be zero. Zero selects the software bilinear
   bank; nonzero banks are unsupported. Nearest/average do not use the LUT.

## Stage 2: coordinates and phases

For one axis, let `T` be the programmed Q4.20 increment and `s = T / 2^20`.
The same rules apply independently to horizontal and vertical coordinates.

| Mapping | Source coordinate at output index u | Initial Q21 state A |
| --- | --- | --- |
| Original | `u * s` | `0` |
| Shift | `(u + 1/2) * s - 1/2` | `T - 2^20` |

Advance integer state by `A += 2*T` for each output; interpret `x = A / 2^21`.
The extra fractional bit preserves half-pixel initialization even for odd `T`.
Reset horizontal state for every processed row and vertical state for each frame.
The accumulator has 21 fractional bits and an unbounded Python integer part;
it is not restricted to the increment register's integer width.

For bilinear, split `x` into `base=floor(x)` and its fraction, then compute:

```text
phase = nearest_even(fraction * 32)
if phase == 32: base += 1; phase = 0
```

Nearest-even (NRE) rounds exact ties to the even integer: 0.5 → 0, 1.5 → 2,
and 31.5 → 32 with a carry. The adjusted base/phase selects samples only;
**it never replaces the accumulator state**.

At 2.625× in original mapping:

| Output | Coordinate | Base | Phase |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 0 |
| 1 | 2.625 | 2 | 20 |
| 2 | 5.25 | 5 | 8 |
| 3 | 7.875 | 7 | 28 |
| 4 | 10.5 | 10 | 16 |
| 5 | 13.125 | 13 | 4 |
| 6 | 15.75 | 15 | 24 |
| 7 | 18.375 | 18 | 12 |

## Stage 3: coefficients and interpolation

`C55/bilinear_coefficients.json` is generated locally with the PC tool and ignored
by Git. The resampler loads this file at runtime; generation is a separate step.
To regenerate the bank and run the resampler from the repository root:

```sh
.venv/bin/python -m C55.generate_coefficients \
  --output C55/bilinear_coefficients.json
.venv/bin/python -m C55.resampler --input input.png --registers C55/registers.example.json --coefficients C55/bilinear_coefficients.json --output C55/outputs/output.png
```

The deterministic JSON has `phases: 32`, `fraction_bits: 6`,
`tap_offsets: [-3,-2,-1,0,1,2,3]`, and `banks: {"0": [...]}`. Bank zero has
32 rows of seven signed 8-bit integer weights. At phase `p`, its weights are
`[0,0,0,64-2*p,2*p,0,0]`, summing to 64. These bilinear weights are exactly
representable at this precision. Loading checks metadata, dimensions, integer
ranges, normalization, and the specified bilinear weights. Arbitrary filters
and additional banks are not accepted. JSON is not a packed hardware memory image.

- **Bilinear:** fetch the quantized phase's coefficients, clamp selected neighbor
  indices, and filter horizontally then vertically per RGB channel. Preserve
  horizontal sums at scale 64; the vertical result has scale 4096. Perform the
  only pixel rounding at the end, nearest-even, then clamp to `[0,255]`.
  `int64` intermediates safely contain the maximum horizontal sum 16,320 and
  vertical sum 1,044,480 for this nonnegative normalized bank.
- **Nearest:** round the unquantized register-driven coordinate half up and clamp
  its index. Phase quantization does not change nearest sampling.
- **Average:** use the unquantized coordinate's floor and floor+1 on each axis,
  clamp neighbors, widen samples before summing, and compute `(sum+2)//4`.
  There is no intermediate horizontal rounding. This is translated 2×2
  averaging, not area resampling or a general downsampling anti-alias filter.

## Accumulation error and diagnostics

Repeated integer addition adds no rounding error in Python. The programmed
increment can differ from the dimension ratio because it was truncated once.
For exact ratio `r = input/output`, define `delta = T/2^20 - r`:

- Original mapping has coordinate drift `u * delta`.
- Shift mapping has coordinate drift `(u + 1/2) * delta`.
- Phase selection adds at most `1/64` input pixel of error relative to the
  programmed coordinate. It does not accumulate into subsequent coordinates.

2.625 is exactly representable in Q4.20; its original coordinates also lie on
the 32-phase grid, so it shows neither error. Nonrepresentable ratios such as
8192/3001 reveal truncation drift and can change selected phases. More accurate
coefficient weights alone cannot remove coordinate or phase-quantization error.

```sh
.venv/bin/python -m C55.analyze_phase_error --registers C55/registers.example.json --output-dir C55/outputs/phase-report
```

The command writes `x.csv`, `y.csv`, and `summary.json`, incrementally with no
full-axis trace stored in memory. CSV rows include exact rational coordinate
numerators/denominators, Q21 coordinates, selected and ideal base/phase pairs,
and separate drift, phase, and total sampling errors. Summaries include maximum
and final drift, maximum phase error, phase-index mismatch counts, and complete
base/phase mismatch counts. Fractions are exact during calculation; reported
error values are converted to floating point for presentation.

Diagnostics compare against dimension-based exact rational coordinates and
nearest-even phase selection. They describe LUT sampling even if the configured
method is nearest/average. They validate configuration against its implied
minimum frame extent; they do not consume or certify an actual image stream.

## Hardware interpretation, compatibility, and maintenance

This replacement intentionally changes C55 output: sampling now follows the
programmed increment, and bilinear uses 32-phase Q6 coefficients and final
nearest-even rounding. Earlier C55 output matched the shared Q11 benchmark
kernel; that compatibility is no longer promised. The benchmark code is unchanged.

Signed 8-bit coefficients normalized to 64, tap offsets, phase origin, rounding,
and intermediate precision are explicit **software conventions**. The
[public Linux driver](https://codebrowser.dev/linux/linux/drivers/media/platform/arm/mali-c55/mali-c55-resizer.c.html)
identifies Q4.20 scaling. Interpreting its coefficient bytes as signed values is
consistent with normalization 64; this is an inference, not proof of this model's
complete arithmetic or evidence that hardware bank zero is bilinear.

The supplied LUT screenshot describes seven coefficient bytes, 32 phases, and
16 sets. Preserve its documented final-index discrepancy and the apparent
`hfilt_tinc` heights/widths typo. The register references show byte bit placement,
not verified memory endianness. No hardware addresses or maximum dimensions are
invented. A C port needs bounded dimensions and sufficiently wide coordinate
and address arithmetic. Hardware equivalence still requires verified phases,
coefficient interpretation, rounding, saturation, boundaries, formats, and limits.

The [boundary document](docs/bilinear-scaler-input-and-boundary-conditions.md) explains
general consistency checks and edge handling. This README defines the executable
contract; [discussion notes](NOTES.md) retain the earlier implementation history.
